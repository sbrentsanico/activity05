### Question 2
> **PO-100035 (BuyerRef ORDER-P300-1790249685768) ended with StatusCode 90, which is not in the documentation. How did you work out what it means, and what does your system now do with the stock that will never arrive?**

Although the official LegacySupply documentation only defines status codes 10 through 40, our adapter encountered an unannounced StatusCode 90 while tracking purchase order PO-100035. Through defensive mapping in our LegacySupplyTranslator, any unrecognized status code automatically maps to our internal domain status SupplierOrderStatus.CANCELLED. When the polling process receives this cancelled state, the adapter logs a warning and immediately terminates the fulfillment pipeline without triggering an inventory restock. Because stock is only credited to internal inventory when an order reaches DELIVERED status (StatusCode 40), the cancelled stock is ignored, preventing phantom items from being added to the database.

### Question 3
> **LegacySupply never tells you how long a session lasts. Measure your session lifetime from your own logs, state the number, and explain how your adapter decides when to sign in again.**

Based on log analysis from our automated status polling probes, LegacySupply session tokens reliably expire after approximately 108 seconds. Rather than relying on static timer estimates or local clock synchronization, our adapter uses reactive session management through LegacySupplySessionManager and LegacySupplyClient. Whenever an API request encounters an HTTP 401 error or E-AUTH-07 error code indicating an expired token, the client invalidates the stored session and immediately requests a new token via POST /api/v1/auth/token. Once the fresh token is acquired, the client automatically retries the original request, ensuring continuous background operations without manual intervention.

Meanwhile, `AutoReorderListener` had dispatched an asynchronous `updateStocks()` call with stale inventory, resulting in Tiangge recording available stock at 3 while our internal order service deducted 6. ### Question 3
> **Order TG-R2X4AP was backordered at 21:10:11 and accepted at 21:13:45, after PO-101886 was delivered at 21:13:37. Trace how the delivery reached your Inventory and what then resumed the backordered order.**

At 21:13:37, the background polling loop in `AutoReorderListener` received `StatusCode 40 (DELIVERED)` from `supplierGateway.trackOrderToDelivery("PO-101886")`. The listener immediately invoked `inventoryService.restock(productId, terminalResult.unitsOrdered())`, which incremented the stock column in the `inventory` table and fired an internal Spring domain event `InventoryUpdatedEvent(productId, name, newStock)`. `BackorderResolutionListener` intercepted this event asynchronously via `@EventListener` and iterated over `backorderTracker.getPendingBackorders()`. Finally, `BackorderResolutionListener` sent an HTTP POST to `POST /orders/TG-R2X4AP/resolution` with `{"status": "ACCEPTED"}`, saved the accepted status to `processedOrderRepository`, removed the order from `BackorderTracker`, and published the updated stock to Tiangge at 21:13:45.
